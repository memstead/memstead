# Question

I want to keep a knowledge graph about my product inside the product's existing git repository, so it is versioned and reviewed together with the code. Which workspace shape should I choose, what do I give up compared with the other shape, and can I switch later?

# Answer A

Choose the filesystem (folder) shape. A folder mem is a plain directory of `.md` files plus a `.memstead/` sidecar holding the config and an append-only `changes.jsonl` provenance log; it has no git history of its own, so the entity files are ordinary tracked files in your product repo and every change to the graph shows up in the same commits and pull requests as the code. Bootstrap it with `memstead init` in an empty directory, or `memstead quickstart` for a one-shot setup that also wires the MCP config for your agent; both refuse to adopt pre-existing `.md` files.

The other shape, the mem-repo, keeps each mem as a named branch inside a separate `mem-repo/.git/` with no working tree; entity bytes exist only as git objects, so nothing appears in your outer repo's checkout for reviewers to diff, and the engine even has a guard that adds `mem-repo/` to the outer `.gitignore` to avoid a gitlink trap. That makes it the wrong fit for your goal.

What you give up with the folder shape: per-mutation git commits with a compare-and-swap on the branch tip, so no transactional multi-entity commits; the `batch-create` / `batch-update` / `batch-relate`, `recover` and `workspace` policy commands refuse with `UNSUPPORTED_WORKSPACE_SHAPE`; the built-in `fetch` / `pull` / `push` transport refuses too (you rely on the outer repo's git instead); provenance is a JSONL log rather than commit trailers, and the change cursor is a timestamp, not a SHA; cross-process concurrent writers are only guarded by the entity-level hash lock, so treat a folder mem as single-writer.

Switching later: the shape is derived purely from whether `mem-repo/.git/` exists at the workspace root, and one workspace may mount folder and git-branch mems side by side. I could not verify a dedicated one-command shape converter. The credible path is `memstead export --format markdown` (or a `.mem` archive) from one shape and re-initialising in the other; commit history and provenance trailers would not carry over, and I have not confirmed the exact re-import steps.

# Answer B

Choose the filesystem-mem shape: `memstead quickstart --repo.` in your repository. The mem becomes a subfolder of plain `.md` entity files that your own git tracks, reviews and merges like code; Memstead keeps no history of its own for it. A `README.md` beside the entities is tolerated and never loaded as an entity.

The other shape, mem-repo (`memstead mem-repo init`), stores every mem as a branch inside an engine-owned `mem-repo/.git`, with every mutation a commit. That directory is deliberately appended to the outer repo's `.gitignore`, because a nested gitdir would otherwise show up as a gitlink; a health warning fires if it is not ignored. So mem-repo content never rides in your code repo's commits, which is the opposite of what you want.

What you give up on filesystem-mem, verified: the atomic `batch-create`, `batch-update`, `batch-relate` commands and `recover` refuse with `UNSUPPORTED_WORKSPACE_SHAPE`; `memstead mem init` refuses too, so it stays one mem; `fetch`/`pull`/`push`/`branch-reset` need git-branch mems. Provenance lands in an append-only `.memstead/changes.jsonl` inside the mem folder, and change cursors are timestamps rather than commit SHAs. The engine's durability answer for folder mems is "survives restart", nothing about being recorded. What you gain: merge conflicts from your repo's branches are a supported case, resolved per entity with `memstead conflicts resolve --side ours|theirs`.

Switching later: the receipt states it means starting a second workspace. Structurally, though, `mem-repo init` in the existing workspace root keeps an existing `workspace.toml` and only refuses if `mem-repo/` already exists, and the shape is detected purely from `mem-repo/.git`, so the folder mem should remain mounted while later mems get branches; an existing folder mem can also be re-attached into a mem-repo workspace with `mem init <name> --storage folder --location <dir> --reattach`. I could not confirm that in-place upgrade end to end, and there is no folder-to-branch conversion of an existing mem.
