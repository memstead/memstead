# Question

A knowledge graph about a codebase goes stale as the code moves on. What can go wrong with a Memstead mem over time, how does Memstead notice, and what does it do about it, automatically or on request?

# Answer A

Four things go wrong. An entity keeps describing a file that has since changed (drift); a file appears that no entity describes (uncovered); a file is deleted while its entity lives on (a prune candidate); and a mem is edited from outside so a running engine's cache is behind the disk. Memstead treats each separately and never repairs content on its own.

The load-bearing primitive is the anchor: a durable sidecar row tying an entity to a source artifact at a grain (span, file, tree, url, entity) with a hash over the prepared form, written in the same commit as the entity. Nothing is stamped as fresh; staleness is computed by re-hashing. `memstead verify-anchors --mem <name>` reports per anchor `resolves`, `drifted`, `recheck` (unstable hash or missing baseline), `unresolvable` (artifact gone) or `unobserved`, with the population it measured so a count is never read as health. The `memstead_health` tool folds this in: its `stale` axis reads anchored entities by anchor state and unanchored ones by a per-type day threshold, and opt-in axes cover dangling links, orphans and derivation baselines.

For a mem built from a source by a binding, change detection targets what moved since the last baseline (git commits, or a per-file mtime/size digest that catches deletions) and renders it as a changed slice in a sync brief; a no-signal case is named rather than shown as empty. `projection verify` measures coverage, accuracy and freshness, records durable findings, and mutates no entity. Deleted files become prune proposals, never automatic deletions; where a git base is retrievable it can separate a clean removal from a model-side edit. The repair itself is the agent's: it works the slice, records a disposition per artifact, and the `#synced` baseline advances only when nothing unexamined remains.

Externally edited mems are handled automatically: before every operation the engine probes each mount's head, reloads what moved, and flags `MEM_RELOADED`. I could not verify how the loop scheduling behaves end to end beyond what these surfaces declare.

# Answer B

Three things go wrong. First, the source moves: files the material describes are edited, added, or deleted. Second, entities age or lose their footing: a claim sits untouched past a threshold, an edge derived from another entity no longer matches that entity's current content, a link points at nothing, or a recorded verification no longer applies because the entity changed. Third, the engine's own in-memory picture falls behind the mem repository when another process commits to it.

Noticing is deterministic and engine-side. Each entity written from a source carries anchors: the artifact path, a grain, a provenance class, a version, and a hash over the prepared artifact. Verification re-observes every anchor and classifies it as resolves, drifted (hash differs on a stable medium), recheck (hash unavailable or medium unstable), or orphaned (artifact gone). Source movement is detected per binding by comparing a stored baseline token against the source's current state: a git commit diff, a graph snapshot diff, or a per-file mtime/size digest that also catches deletions. Health separately reports entities older than the schema's `staleness_threshold_days` (deferring to anchor state when one exists), dangling links, and stale derivation edges. Check records go `check_stale` once the content hash moves. Every operation probes the mem's head and reloads if it advanced, emitting a `MemReloaded` warning.

What it does about it is deliberately limited. Verify writes durable findings (drifted, uncovered, unresolvable-anchor, unanchored-mention, queued-for-adjudication) and a fidelity report, but never touches an entity. The sync brief presents the changed slice, open findings, and prune proposals to an agent, which performs the repairs through the normal mutation surface; deletions are proposed, never automatic, and authored entities are never prune targets. Baselines advance only when the agent records dispositions for the whole slice. A loop rotation picks due bindings with backoff. Whether a scheduled full walk occurs depends on `full_resync_every`. The engine never repairs content on its own.
