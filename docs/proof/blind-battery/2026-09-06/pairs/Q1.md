# Question

I have never seen Memstead. Explain how it works end to end: what happens from the moment an AI agent asks to write a fact until that fact is a file in git, where the checks sit along the way, and what the agent reads back afterwards. One page, for a developer.

# Answer A

An agent talks to Memstead over MCP. A write is a `memstead_create` (or `memstead_update`) call naming a mem, an entity type, a title, sections, metadata and optional relations; the handler checks the note, resolves role and identity, takes the single engine lock and passes the call to the engine.

The engine first compares the mem's current head with its cached head and reloads if another writer advanced it. Then a fixed chain of refusals runs before any byte is written: the mount must be writable; the type must exist in the mem's pinned schema; section keys, reserved metadata keys, typed and enum field values, anchors and embedded headings are validated; the title becomes a slug and id, and a non-stub duplicate refuses; missing required sections or fields refuse with recovery payloads; each inline relation passes the same gates as `memstead_relate` (target grammar, cross-mem policy, rel-type vocabulary and shape, acyclicity); wiki-links without a backing relation refuse; then the markdown is rendered and block-tier format, required-outgoing and constraint checks run, warn-tier ones becoming warnings. A `dry_run` stops here and returns the prospective hash.

The file is YAML frontmatter, `# title`, one `## heading` per section and a `## Relationships` list of `[[wiki-links]]`. For a git-branch mem the backend stages it, then `commit` writes a blob, edits the parent tree and creates one commit on the mem's branch, author derived from the client, trailers for Tool, Actor, Client, Role, Identity and note; if the ref moved meanwhile the commit fails as a hash mismatch instead of rebasing, and a checked-out worktree is synced with `git read-tree`. A plain folder mem writes the file atomically and appends a JSONL changelog; no git commit happens there.

After the commit the engine re-parses what it wrote, upserts the entity into its in-memory store, auto-stubs missing relation targets, refreshes search indexes and records the new head as its own write. The agent gets back id, file_path, `_hash`, `write_id` (the commit SHA), warnings, type_guidance, incoming edges and `durable`/`durability_basis`. Later it reads the entity as markdown with `_hash` in the frontmatter via `memstead_entity`, sends that hash as `expected_hash` on update for optimistic locking, and lists what moved with `memstead_changes_since`.

# Answer B

Memstead keeps knowledge as mems: named collections of typed markdown entities, each pinned to one schema and mounted in a workspace, stored either as plain `.md` files in a folder or as git objects on a branch inside a mem-repo. An agent talks to it over MCP, a JSON-RPC-over-stdio server with twenty tools; the CLI exposes the same operations.

Writing a fact means calling `memstead_create` (new entity) or `memstead_update` (changing one). For an update the agent first reads the entity with `memstead_entity`, whose response carries a `_hash` token; a content-changing update must return it as `expected_hash`, and a stale token is refused with `HASH_MISMATCH` instead of overwriting a concurrent write.

Before anything else the engine checks whether the mem's on-disk head moved since it last looked, reloading if so; only then does the operation run. Next the runtime validator checks the payload against the pinned schema: unknown sections, undeclared or read-only metadata fields, out-of-enum values, embedded headings that would corrupt parsing, missing required sections or fields, and relationship types outside the vocabulary all refuse with a typed error code plus a recovery payload. Body wiki-links become edges, missing targets become stubs, and a link without a backing relation refuses; `dry_run: true` runs the same validation without writing.

If validation passes, the entity is serialised to canonical markdown in deterministic order. On a git-branch mem the bytes land as exactly one commit, with a compare-and-swap on the branch tip so a second process cannot clobber it; the message carries `Tool`, `Actor`, `Client`, and optionally `Role` and `Identity` trailers under a fixed engine committer. On a folder mem the file is written atomically via temp-and-rename and a JSONL changelog line records provenance, with no commit-level CAS. The engine then re-parses the written bytes into its in-memory store so memory mirrors disk.

The agent reads back a `write_id` (the commit SHA, or a synthetic token on folder mems), the new `content_hash`, a `durable` flag with its basis, and warnings such as auto-stubbed targets or a `MEM_RELOADED` drift notice. I could not verify request field names beyond those stated.
