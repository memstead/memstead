Choose the filesystem-mem shape: `memstead quickstart --repo .` in your repository. The mem becomes a subfolder of plain `.md` entity files that your own git tracks, reviews and merges like code; Memstead keeps no history of its own for it (memstead-cli/src/setup.rs `shape_disclosure_in`; memstead-cli/src/commands/quickstart.rs layout comment and `mem_in_subfolder`). A `README.md` beside the entities is tolerated and never loaded as an entity (memstead-base/src/entity/source.rs `find_markdown_files`).

The other shape, mem-repo (`memstead mem-repo init`), stores every mem as a branch inside an engine-owned `mem-repo/.git`, with every mutation a commit. That directory is deliberately appended to the outer repo's `.gitignore`, because a nested gitdir would otherwise show up as a gitlink; a health warning fires if it is not ignored (memstead-cli/src/commands/mem_repo.rs `run_init`; memstead-base/src/workspace_root.rs). So mem-repo content never rides in your code repo's commits, which is the opposite of what you want.

What you give up on filesystem-mem, verified: the atomic `batch-create`, `batch-update`, `batch-relate` commands and `recover` refuse with `UNSUPPORTED_WORKSPACE_SHAPE` (memstead-cli/src/setup.rs `FILESYSTEM_CANNOT`, `unsupported_workspace_shape_message`); `memstead mem init` refuses too, so it stays one mem (memstead-cli/src/commands/mem.rs, the `CliEngine::Filesystem` arm); `fetch`/`pull`/`push`/`branch-reset` need git-branch mems (memstead-cli/src/cli.rs). Provenance lands in an append-only `.memstead/changes.jsonl` inside the mem folder, and change cursors are timestamps rather than commit SHAs (memstead-base/src/filesystem/changelog.rs; memstead-base/src/backend.rs `current_head`). The engine's durability answer for folder mems is "survives restart", nothing about being recorded (memstead-base/src/workspace.rs `durability_basis`). What you gain: merge conflicts from your repo's branches are a supported case, resolved per entity with `memstead conflicts resolve --side ours|theirs` (memstead-cli/src/commands/conflicts.rs).

Switching later: the receipt states it means starting a second workspace (memstead-cli/src/setup.rs). Structurally, though, `mem-repo init` in the existing workspace root keeps an existing `workspace.toml` and only refuses if `mem-repo/` already exists, and the shape is detected purely from `mem-repo/.git`, so the folder mem should remain mounted while later mems get branches; an existing folder mem can also be re-attached into a mem-repo workspace with `mem init <name> --storage folder --location <dir> --reattach` (memstead-cli/src/commands/mem_repo.rs `write_default_workspace_toml`; memstead-base/src/workspace_store.rs `is_mem_repo_shaped`; memstead-base/src/error.rs `ConfigAlreadyExists`). I could not confirm that in-place upgrade end to end, and there is no folder-to-branch conversion of an existing mem.
