Memstead keeps knowledge as mems: named collections of typed markdown entities, each pinned to one schema and mounted in a workspace, stored either as plain `.md` files in a folder or as git objects on a branch inside a mem-repo (engine--mem, engine--storage-backend). An agent talks to it over MCP, a JSON-RPC-over-stdio server with twenty tools; the CLI exposes the same operations (engine--mcp-tool-surface).

Writing a fact means calling `memstead_create` (new entity) or `memstead_update` (changing one). For an update the agent first reads the entity with `memstead_entity`, whose response carries a `_hash` token; a content-changing update must return it as `expected_hash`, and a stale token is refused with `HASH_MISMATCH` instead of overwriting a concurrent write (engine--entity-read-projection-surface, engine--update-mutation).

Before anything else the engine checks whether the mem's on-disk head moved since it last looked, reloading if so; only then does the operation run (engine--reload-before-operation-coherence). Next the runtime validator checks the payload against the pinned schema: unknown sections, undeclared or read-only metadata fields, out-of-enum values, embedded headings that would corrupt parsing, missing required sections or fields, and relationship types outside the vocabulary all refuse with a typed error code plus a recovery payload (engine--runtime-validator, engine--create-mutation). Body wiki-links become edges, missing targets become stubs, and a link without a backing relation refuses; `dry_run: true` runs the same validation without writing (engine--create-mutation).

If validation passes, the entity is serialised to canonical markdown in deterministic order (engine--entity-to-markdown-generator). On a git-branch mem the bytes land as exactly one commit, with a compare-and-swap on the branch tip so a second process cannot clobber it; the message carries `Tool`, `Actor`, `Client`, and optionally `Role` and `Identity` trailers under a fixed engine committer (engine--git-tree-mem-writer, engine--per-mem-commit-and-provenance-trailer-layer). On a folder mem the file is written atomically via temp-and-rename and a JSONL changelog line records provenance, with no commit-level CAS (engine--filesystem-mem-writer). The engine then re-parses the written bytes into its in-memory store so memory mirrors disk (engine--create-mutation).

The agent reads back a `write_id` (the commit SHA, or a synthetic token on folder mems), the new `content_hash`, a `durable` flag with its basis, and warnings such as auto-stubbed targets or a `MEM_RELOADED` drift notice (engine--mcp-tool-surface, engine--create-mutation). I could not verify request field names beyond those stated.
