There is no semantic or vector search to turn on, and no embedding model to choose. The engine has no embedding, vector, or similarity code path anywhere, and no configuration key for one; the only search machinery is a per-mem, in-RAM tantivy full-text index (memstead-base/src/search_index/mod.rs: `build_all`; search_index/writer.rs: `MemIndex`). Your searches feel literal because they are literal by design.

How ranking actually works: every query becomes a tantivy boolean query and hits are ordered by BM25 score (search_index/query.rs: `execute_on_mem`, `build_tantivy_query`). Text is tokenised by splitting on non-letters, lowercasing, and ASCII-folding diacritics; there is deliberately no stemming, so "running" does not match "run", though "Häuser" does match "hauser" (search_index/tokenizer.rs: `analyzer`). The query shape is flat: `any` (OR across terms, more matching terms rank higher), `not` (exclusion), `phrase` (exact adjacency), and `field` to narrow to the title or one section key (ops/mod.rs: `Query`). Fields are weighted from the schema: each type's `title_weight` and each section's `search_weight` become boosts, maxed across types sharing a key; a section weighted 0 is skipped unless you target it by `field` explicitly; a low-weight metadata keys-and-values field is also searched (query.rs: `resolve_target_fields`, `title_weight`, `section_weight`). Each hit reports `matched_terms` and an illustrative `score_breakdown` so you can see which fields carried the score (search_index/snippets.rs: `compute_matched_terms`, `compute_score_breakdown`).

What to do instead to find things by meaning:

1. Enumerate variants yourself in `any`: morphological forms and synonyms ("auth", "authentication", "login", "sign-in"). The engine expects the caller to do this (ops/mod.rs: `Query` doc; memstead-mcp/src/tools/graph.rs: query parameter description).
2. Use the graph as the semantic layer. `expand_via` follows named relationship types from your text hits to their neighbours, scoring them at `0.5^depth`, and `related_to` with `depth` and `direction` returns a proximity-ranked neighbourhood around a known entity (ops/search.rs: `expand_hits`, the `related_to` sort; graph.rs: `SearchParams`).
3. Combine text with structural filters (`entity_type`, `filters`, `range_filters`, `edge_type`) to cut noise rather than relying on the score alone (ops/search.rs: `search`).

If you need true embedding search, you would have to build it outside the engine over the markdown files; nothing in the engine can host it today.
