Choose the filesystem (folder) shape. A folder mem is a plain directory of `.md` files plus a `.memstead/` sidecar holding the config and an append-only `changes.jsonl` provenance log; it has no git history of its own, so the entity files are ordinary tracked files in your product repo and every change to the graph shows up in the same commits and pull requests as the code (engine--storage-backend, engine--filesystem-mem-writer, engine--filesystem-mem-jsonl-changelog). Bootstrap it with `memstead init` in an empty directory, or `memstead quickstart` for a one-shot setup that also wires the MCP config for your agent; both refuse to adopt pre-existing `.md` files (engine--cli-cold-start-quickstart-and-schema-scaffold-surface, engine--cli-command-surface).

The other shape, the mem-repo, keeps each mem as a named branch inside a separate `mem-repo/.git/` with no working tree; entity bytes exist only as git objects, so nothing appears in your outer repo's checkout for reviewers to diff, and the engine even has a guard that adds `mem-repo/` to the outer `.gitignore` to avoid a gitlink trap (engine--git-tree-mem-writer, engine--outer-repo-gitignore-guard). That makes it the wrong fit for your goal.

What you give up with the folder shape: per-mutation git commits with a compare-and-swap on the branch tip, so no transactional multi-entity commits; the `batch-create` / `batch-update` / `batch-relate`, `recover` and `workspace` policy commands refuse with `UNSUPPORTED_WORKSPACE_SHAPE`; the built-in `fetch` / `pull` / `push` transport refuses too (you rely on the outer repo's git instead); provenance is a JSONL log rather than commit trailers, and the change cursor is a timestamp, not a SHA; cross-process concurrent writers are only guarded by the entity-level hash lock, so treat a folder mem as single-writer (engine--storage-backend, engine--filesystem-mem-writer, engine--cli-command-surface, engine--filesystem-mem-jsonl-changelog).

Switching later: the shape is derived purely from whether `mem-repo/.git/` exists at the workspace root, and one workspace may mount folder and git-branch mems side by side (engine--workspace-root-discovery-and-shape-detection, engine--workspace, engine--mem-lifecycle-operations). I could not verify a dedicated one-command shape converter. The credible path is `memstead export --format markdown` (or a `.mem` archive) from one shape and re-initialising in the other; commit history and provenance trailers would not carry over, and I have not confirmed the exact re-import steps (engine--mem-archive-export-surface).
