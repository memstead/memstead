# Report trust origin at entity and check-row grain, decided at merge time

## Decision
We will report the first-party / third-party trust class per ENTITY and per CHECK ROW, not only per mem, and we will decide it at write time rather than deriving it from content at read time. A proposal merge records, for every adopted slug in the mem's proposal record, one prepared hash per load-bearing section of the body it landed; `Engine::entity_origin_class` checks whether those marks still hold and reports third-party while any marked section is still the contributor's bytes, the mem's class once the owner has rewritten every one of them. How that record is read is owned by one type: `ProposalRecord` answers which marks a slug makes effective, which row makes them effective, and whether the record is structurally defective, and every write that has to follow a mark asks it instead of modelling the rules again.

Corrected 2026-09-26: this said one hash over the whole load-bearing form plus the schema pin the hash was computed under. Adversarial review found three defects in that shape, all fixed the same day. One hash over the whole form collapses a type's load-bearing sections to one bit, so an owner tightening one of three would have had the other two served as the workspace's own claim. A hash computed under a schema pin depends on which sections that pin calls load-bearing, so a repin made every mark unconfirmable and, because nothing retires a mark, permanently and unclearably third-party; a retype did the same in the other direction. Per-section hashes carry their own section key, so the comparison needs neither the pin nor the type, and the pin is no longer recorded. An `adopt_with_changes` records no mark, because the owner typed that body, and neither does a deletion. A check row's prose is classified against the deployment's own writing identities, declared through `Engine::declare_owner_identities` on the composition layer. On markdown surfaces the class is stated as `_origin` and a third-party body is contained in a delimiter whose nonce is derived from that body and lengthened until the body cannot contain it.

## Context
The mem grain answers for a whole installed mem and says nothing about a writable mem that accepts contributions. There, a body merged in from a fork is a stranger's prose sitting in a mem every read surface calls first-party, served in the same undifferentiated document as the owner's own entities, so an agent reading the mem to answer a question has no way to treat those sentences as quoted data rather than as part of the document it was told to trust. The authorship was already recorded (the merge commits an adopted entity under the proposer's identity) and only the read surfaces were silent. Two further facts forced the shape. The caller-declared identity trailer cannot be the lever, because the party that writes a body also chooses that string, and trust derived from it would be trust the writer grants themselves. And the text channel carried no origin token at any grain while the JSON envelope had one, so the channel a cold agent actually reads was the silent one.

## Consequences
- A host that already quarantines on `third-party` quarantines a merged contribution with no change on its side: the class only ever tightens, and the wire vocabulary keeps its two tokens and its one key.
- The comparison is the load-bearing form rather than the file hash, so the owner's bookkeeping edits (a metadata stamp, a notes-only change) no longer promote a stranger's claim to first-party, and a mark expires per section, on the edit that rewrites that claim. The cost is that an owner who rewrites every load-bearing section while leaving a contributor's notes in place gets first-party for the whole entity.
- A write that MOVES a marked body carries its marks where that write happens: a rename moves the label onto the target slug in the terms the read uses (it flattens every proposal in order, so the marks are written where nothing later can retire them), a re-keying retype carries the section key, and the hashes themselves are followed at the three wiki-link retargets (a rename of a linked entity, a mem rename workspace-wide, a published archive's retarget to its leaf name). The invariant is about moves, not copies: `mem fork` copies bodies into a new mem and deliberately drops the proposal record, so a fork of a mem serves its adopted bodies as first-party. That is the boundary the design draws, and it is visible: publishing a fork publishes a contributor's prose unlabelled.
- The cost is that four mutation paths plus the archive export now touch the proposal record, a file previously written only by a merge, and that any future rewrite of marked bytes must join them. Every one of those writes reads the record through its owning type, which is what stops the write and the read drifting apart; a write that models the flattening itself is the defect this change produced four times. The enumeration test narrows that search inside `memstead-base` (a new call in a file that carries no marks fails it) but does not close it: a new call in a file already listed, an indirect caller through `retarget_mem_links`, or a call in another crate all pass. Owner: whoever adds the call site. Sunset: the day the rewrite helpers carry the record themselves, which would remove the cause instead of watching it. The alternative was read-time inference from matching content, which is unsound: 23 type and schema pairs in the shipped catalogue declare exactly one load-bearing section, so a whole mark is one line there and a contributor can aim the collision.
- The check-row class tightens on both inputs, the declared identity and the class an archive sealed. Neither can win first-party on a third-party mem, because both are the publisher's own bytes; the sealed class is honoured only where it makes a vouched archive's row stricter.
- A rejection retires nothing, because a rejection is the owner declining a change and not evidence that they rewrote the claim. Read the other way, a contributor could have cleared a standing mark at will by proposing anything against an already-adopted slug and having it rejected.
- The proposal record grows two additive, serde-default fields, so every existing record still parses, and a workspace that takes no contributions reads exactly as before. A test that predicts the record's bytes now has to predict the mark too.
- Absence of evidence inherits the mem's class rather than resolving third-party. Resolving unknown to third-party globally would flip every entity in every existing mem, and a token that reads third-party everywhere tells a host nothing.
- A first origin read per session costs one backend read per writable mem (the proposal record), memoised on the derived key and invalidated where the community memo is.
- Containment is byte-visible: a mem holding an adopted body exports different bytes, so a sealed archive and the reconstruction measurement move for that mem. The delimiter is derived rather than random precisely so those bytes stay reproducible, and a mem with no adopted body is byte-identical to before.
- `render_entity_markdown` stays label-free, which is what keeps anchor hashing, preparation and projection byte-stable; the serving variant takes the class as an explicit argument, so a surface that forgets it renders the canonical form rather than a wrong label.

## Options

- Derive the class at read time from the `Identity:` commit trailer, as first requested: rejected, because identity is caller-declared and unverified, so a contributor would choose their own trust class, and because the governing principle fixes origin as decided at adopt or write time and never re-derived.
- Key the staleness comparison on the entity's file hash: rejected after it was pointed out that a metadata stamp or a notes-only edit by the owner would silently promote a stranger's load-bearing prose to first-party.
- Reuse the proposal record's existing `content_hash` (the proposed version's hash, stamps excluded) instead of recording a landed mark: rejected for the same reason, and because that hash is the fork's body before the merge normalises self-links, so a comparison against the landed entity would quietly never match.
- Add a third wire token or a second trust field for the new grain: rejected as response-shape growth a consumer must learn; tightening the existing `origin` key needs nothing from the consumer.
- Mark the mem's `authors` list or a per-mem config field as the owner-identity set: rejected because that file lives in the mem-repo a contributor writes to, which would make first-party forgeable.
- Build a deployment-declared owner-identity set for check rows before a path existed for a stranger's row to reach the owner's ledger: initially rejected as apparatus ahead of need, then adopted once two real ingress shapes were named, in both of which the identity is assigned by the owner's own side and therefore is a deployer's fact rather than an authoring party's claim.

## Notes

Reported by a peer agent reading the engine from outside as a generic finding, with no consumer context attached, and translated into the engine's own fixtures before any of it touched this repo. Two corrections came out of the review of the report itself: a per-hit `origin` field already present on the search envelope was a copy of the mem's class rather than half of this work, and the serving binary named as a third engine surface is not part of the open engine at all. Implementation defect found while building: a fork's deletion is also an `adopt`, and the store still holds the owner's pre-delete entity when the record is written, so marking on the disposition alone stamped the owner's own body as a stranger's; the mark now requires an actual landed write.

2026-09-26, from an independent adversarial review of the first implementation, beyond the three defects the Decision section records: a later rejected proposal retired a standing mark, because the reader inferred retirement from an absent hash and a reject entry carries none; a rename stranded the mark, since matching was by slug alone; an unparseable proposal record failed open and silently relabelled every adopted body as the workspace's own; the chunked read delivered contributor bytes without the containment frame from chunk two onward; the CLI export envelope and a duplicated CLI health renderer were never brought along; and the sealed archive field was write-only and unvalidated. All fixed, each with a test that fails without its fix. The duplicated health renderer was removed rather than gated, per cause before gate: one function now serves both surfaces. A first attempt to fix the rename by matching marks on section content alone was reverted when the engine's own fixture proved the false-positive risk real, an unrelated entity sharing one boilerplate section was branded as a contributor's.

2026-09-26, second independent review, which found the replacement wrong too and six more defects. Matching a slug with no mark against WHOLE marks was still unsound: 23 type and schema pairs in the shipped catalogue declare exactly one load-bearing section, so a whole mark is a single line there, and a contributor could aim the collision by getting a copy of an owner's entity adopted. Content inference is gone entirely: a rename and a re-keying retype now carry the marks in the mutation's own commit, and the read is an exact lookup. Also fixed: the test for the rejection guard was vacuous, because an all-reject merge writes no record at all, so it passed with the guard deleted (a mixed merge proves it now, and deleting the guard fails it); a retype with a `section_map` laundered a body, since a mark's hash covers its key; the chunk reframing wrapped the engine's own computed appends in the stranger's frame, teaching a reader that the engine's own relation graph is untrusted; a structurally empty mark map inverted the whole mem, because `all()` over nothing is true; the check-row class could be talked into first-party by a publisher-supplied identity on a third-party mem; the search and list TEXT channels still served a contributor's lead section unlabelled, which is the very gap the change was justified by; a mem vouched first-party by the deployment had its own adopted bodies served as the vouching deployment's prose, because the mark scan skipped non-writable mounts; and the fail-closed branch was silent, so an operator saw their own mem called a stranger's with no stated cause.

The sealed archive field was reported as write-only, and that was true of the path it had: an archive row carries no structured finding, so the health findings map it was read from is always empty for an archive mount. It is load-bearing now through the entity read's provenance block, where the sealed `method` note actually reaches a reader.

2026-09-26, third independent review, which found nine more, including one of the same class as a defect it had already flagged. The sealed class was consulted BEFORE the local reading, so a publisher sealing `origin: first-party` on a mem nobody vouched for served its own checker prose unlabelled: the identity hole closed one round earlier, displaced one field over onto a more publisher-controlled lever. A wiki-link retarget rewrote marked bytes and dropped the mark, from a rename of a linked entity and from a mem rename, both ordinary owner housekeeping and both plantable by one wiki-link in the proposed body. The retype re-keying loop read its own writes, so a chained or swapped `section_map` destroyed one mark and left the content at the end of the chain unmarked. The rename re-key clobbered an existing record entry on a slug collision, corrupting the audit trail the history reader reports from. A deployment declaration did not invalidate the mark memo, so call order could reopen the vouched-archive hole. The empty-mark case was a silent retirement rather than the refusal the changelog claimed. The search and list text-channel containment shipped with no test at all, and deleting both its branches left the suite green. All fixed, each with a test verified to fail without its fix.

2026-09-26, fourth review. Two blockers, both mine from the round before. The archive export's retarget to a published leaf name was the third site that moves marked bytes, so a published mem forgot which of its bodies came from a contributor and the first deployment to vouch for it served that contributor's prose as the owner's own. And the retype's re-keying wrote a structurally empty mark map when nothing held, which the round-three fail-closed reading then treats as a record defect: adopt a contribution, rewrite it in your own words, retype it, and the mem's whole origin labelling was bricked. The rename's collision path also failed open (it dropped a mark rather than moving it into a mark-less entry), and four claims in the changelog and here were stronger than the code. All fixed; the export carry was itself written wrong first (the section tuple read headings as content, so it silently carried nothing) and the test caught it.

2026-09-26, seventh review, which found two more in the function the sixth round had just rewritten, and named the cause exactly: the write path kept a SECOND projection of the read's flattening rules, in another module, kept in sync by a doc comment claiming it was. Four rounds of one-position-over defects were the price of that copy. Concretely this time: the rename cleared or overwrote the entry whose structurally empty mark map makes the read fail the whole mem closed, so an ordinary rename lifted a quarantine and erased its evidence; and the relocation branch moved the first row naming the slug rather than the row whose marks were effective, which carried a rejection's reason and content hash onto another slug and took the re-proposal gate with it. The fix removes the copy: the rules live on `ProposalRecord`, the read and every mark-following write consume them, and the rename refuses a record the reader calls defective instead of repairing it.

2026-09-26, sixth review, which found the fifth round's own fix wrong in the same way the three before it were wrong, one position over. The rename decided the collision PER PROPOSAL while the read flattens every proposal into one slug map, last word wins. So a later proposal holding a mark-less entry for the rename's target retired the marks the rename had just moved there, and a contributor's untouched body read first-party again: adopt one slug, later land an `adopt_with_changes` on another, delete that entity, rename the first onto the freed slug. The fix stops patching per entry and computes the flattened outcome the way the read computes it, which is the shape the three previous collision defects were all missing. Also: whether a mark-less entry followed a rename depended on whether an unrelated proposal in the same record carried a mark, and the function copied where its own name said move.

2026-09-26, fifth review, which lifted nothing and found the fourth round's export fix half-done: the record keys by the whole slug, subdirectories included, and the new helper derived it with `file_stem`, so it carried nothing for a NESTED entity, which is the only shape whose export retargets links at all. The fix that was written for hierarchical mems therefore did not work for hierarchical mems. Also: the rename's collision path still dropped the marks when the target entry carried marks of its own (the deleted entity's, matching nothing), and one of the two new export tests passed through an early return without exercising the guard it named. All three fixed.

2026-09-26, eighth review, which refuted its own predecessor's prediction: no further defect of the class that had recurred five times, which is the evidence that removing the duplicated rules removed the cause. It found two of a sibling class instead, both places where a write RE-DERIVES something rather than asking its owner, and both fixed here. The export re-parsed each entity's section map without a schema, but the store's map is schema-shaped (a catch-all section's value is the join of its own content and every undeclared heading), so a mark keyed by a catch-all could never carry and a published archive shipped a mark that no longer held over its own bytes; the export now derives the map with the schema it already embeds. And the mem-rename sweep handed a section body to the whole-file rewriter, whose mask trims a leading `---` block as frontmatter and therefore leaves a fenced link inside it unmasked, so the section pass and the file pass could disagree and a mark end up hashing bytes the file does not hold; there is now a section-safe form, and a test that pins the difference. The refusal `structural_defect` documents is now honoured by all four writers rather than by the rename alone, with a test.

What the reviews left standing, recorded as known and not fixed here. The proposal brief and `memstead_diff --include-content` render a contributor's title and bodies with no label and no containment, which is the review surface where an injection targets the reviewing agent. A third-party mem's `llms-full.txt` contains nothing per entity, on the argument that the header speaks for the document, an argument the chunking fix rejected one surface over; the same document also wraps the engine's own `_Type:` line inside the frame, and states no cause when a mem fails closed. `mem fork` copies bodies without their marks, so a fork serves adopted bodies as first-party: the invariant covers moves, not copies, and either the fork carries a marks-only record or this stands, which is a decision beyond this change. The enumeration test does not see a new rewrite call in a file already listed, an indirect caller through `retarget_mem_links`, or another crate. And a very small `token_budget` on a third-party entity frames the engine's own frontmatter as quoted data, which a caller can ask for and an attacker cannot.

Three more, recorded rather than fixed. The `PROPOSAL_RECORD_UNREADABLE` cause rides the entity read only, so a search, list, health or export on a quarantined mem shows the conservative label with no reason. `memstead_health`'s description does not mention the per-finding author and `origin` its `checks` axis now carries, because the description is at its hard 2048-byte cap and the change is additive, unlike `memstead_search`, whose `origin` grain changed and which was therefore re-cut to fit. And an adopt from a fork of one's OWN mem marks the owner's own prose third-party permanently, because the merge compares nothing between proposer and merger: fail-closed, but a label that fires on the owner's own text is how a trust signal stops being read, and the entity grain has no counterpart to the check row's declared owner identities.
