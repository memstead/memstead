# One preparation slot, three flavours, two engine touchpoints

## Decision
One slot, one REGISTRY, two engine TOUCHPOINTS — every flavour is an implementation behind the same seam, so landing any one leaves the others pluggable without redesign. (1) DECLARATION: the slot stays a per-source string identifier, resolved against an engine-owned registry of implemented preparations; `validate_binding` narrows from refuse-always to refuse-UNKNOWN-identifier (same `PreparationUnsupported` shape, now meaning "not in this engine's registry"), and the brief-render refusal retires with its residual "facet" wording — both refusal paths move together. An empty registry preserves today's behaviour exactly. Parameterisation stays out of v1; the identifier is opaque to the hash. (2) TOUCHPOINT A — PREPARED FORM (serves content and code-map): the anchor-observation path asks the registry for the artifact's prepared form before hashing. Content preparation `entity-load-bearing`: the entity grain's prepared form is the ordered concatenation of the sections the schema declares load-bearing (schema-side declaration; absent a declaration, the type's REQUIRED sections are the default), serialized stably (schema section order, key + body) and hashed through the existing minimal text canonicalization — this closes the entity grain's never-hashed gap and makes anker's zero-false-positive metric mechanical: notes churn is invisible, a load-bearing edit breaks the hash. The `url` grain acquires its prepared form through the same canonicalization over the artifact content supplied at observation, `hash_stability: unstable` as the sensible default (a break resolves recheck, not drifted); a reducing url preparation is a later registry entry, not v1. Code-map preparation reduces a scoped codebase file to its interface digest (exports, signatures, imports — formatting and comments invisible); the skepticism check's answer is precisely the drift contract: an agent can build a map, but only an engine-owned prepared form participates in prepared-hash/stability drift detection and impl-version invalidation — the map STAYS TRUE by construction instead of by re-derivation. (3) TOUCHPOINT B — DELIVERY (serves plenum): the ingest delivery path asks the registry for the source's unit sequence. The contract names plenum's two sub-needs separately and both bind: UNITIZATION (a unit is addressed `file#unit-key`, keys stable under content growth) and TOTAL ORDER (derived from unit-intrinsic keys, never discovery or filesystem order; first run and change run produce the same sequence for the same source state; a change run delivers new/changed units at their ORDERED positions). A preparation implements one or both touchpoints; the registry records which. (4) IDENTITY/INVALIDATION: identifier + `PREPARATION_IMPL_VERSION` stay hashed into the binding identity; the version stays GLOBAL in v1 — any behavioural change to any registered preparation bumps it and invalidates every finding keyed on the old hash by construction (safe over-invalidation; per-identifier versions are a later refinement that must never weaken invalidation). The standalone anchor-verify operation inherits all of this unchanged — it reads prepared forms through the same observation path. (5) The `path` grains' existing prepared-form behaviour (minimal text canonicalization / raw-byte binary) is untouched; PDF/DOCX/audio conversion stays a NON-GOAL per the standing backlog decision — agent-side extraction plus the raw-byte fallback suffice, documented at the point of use.

## Context
Three independent consumers converged on the reserved `Source.preparation` slot within two weeks, each wanting a different job: CONTENT preparation (anker Befund 5, `../anker/methods/engine-befunde.md`): hash only the schema-declared load-bearing sections of an entity so dependent conclusions detect "the load-bearing sentence changed", not "a comma landed in the notes" — false-positive drift to zero; DELIVERY preparation (plenum Befund 17, `../plenum/methods/engine-befunde.md`): sub-file unitization (one file carrying many delivery units) plus a deterministic total order holding across first run AND change run — "same source state → same sequence" as an ENGINE property, not caller discipline; CODE-MAP preparation (WOENENN primary needs statement, `dev/woenenn-needs-statement-2026-08-18.md`, item 3): cut per-iteration ingest cost over a ~200-scoped-file codebase, more mems coming, not blocking. Today the slot is a bare optional string refused unconditionally at binding validation (`PreparationUnsupported`) and again at brief rendering; `PREPARATION_IMPL_VERSION` is 0 and already participates in the binding hash — the findings-invalidation-on-bump property is designed in. The grain baseline (corrected per the design review): W5's landed entity-anchor observation already hashes the entity grain over canonical rendered markdown through `prepared_content_hash` — so for a source that DECLARES the content preparation, the flavour is a prepared-form CHANGE (raw rendered form → load-bearing sections), not a first-ever hash; the invalidation story holds either way since the declared identifier itself changes the binding hash. The `url` grain remains without a hash path, and the `tree` grain is recorded-but-unhashed. `Anchor.hash` is documented as a hash over the prepared form, "never raw bytes" — the engine promises preparation at the data structure and refuses it at validation.

## Consequences
Landing order follows the channels' own instruction: entity and url grains first (content preparation is the first registry entry), delivery second, code-map third — each an independent follow-up plan consuming this design (flywheel 09 bundle names them). Non-foreclosure is structural: one registry, two orthogonal touchpoints; content and code-map never touch delivery's seam and vice versa. The first landed implementation bumps `PREPARATION_IMPL_VERSION` to 1 and thereby demonstrates the documented findings-invalidation behaviour; the migration test updates to expect the narrowed refusal rather than deleting. Docs correct in both directions: the GLOSSARY's "reserved for non-text mediums (PDF, DOCX, audio)" claim — contradicted by all three actual consumers, all on text and graph mediums — is replaced by the registry/touchpoint description with the PDF non-goal at the point of use. The deliberate residue the design states rather than hides: grains other than path/entity/url (`tree`) keep their recorded-but-unhashed state until a code-map preparation lands — that flavour is exactly the mechanism that will close it.

## Options

Rejected: building one flavour now and designing later — three independent consumers are the argument FOR the design pass, and a single landed flavour is the foreclosure risk the SPEC forbids. Rejected: a typed enum for the declaration — the registry-resolved string keeps the wire format stable, lets private/embedded engines register their own preparations, and the hash treats the identifier opaquely either way. Rejected: per-facet parameters in v1 — no consumer asked for them; the extension point (identifier grammar) is noted, not built. Rejected: a per-identifier impl version in v1 — finer-grained invalidation buys little while the registry is small and risks under-invalidation bugs; global-bump is safe. Rejected: PDF flavour — standing backlog decision, stays out. Considered and deferred: making delivery order keys schema-declarable — the adapter owns them in v1; a schema-side vocabulary can layer on without changing the contract.
