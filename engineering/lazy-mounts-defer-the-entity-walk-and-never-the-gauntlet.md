# Lazy mounts defer the entity walk and never the gauntlet

## Decision
`MountLifecycle::Lazy` is behaviourally real: a lazy mount resolves its METADATA half at boot (config, provenance, schema pin — a broken pin quarantines exactly as an eager mount's would) and defers the entity walk to the first operation that needs the mem. `Engine::ensure_mems_loaded` is the trigger, called at the top of the per-operation `reload_if_stale` funnel: a scoped operation loads exactly its mem; a workspace-scoped or cross-mem-reaching one loads every deferred mem first — the scoping rule is that a handler may scope only when its WHOLE answer lives in the named mem, and every cross-mem form (incoming edges, community context, graph-walking search, the workspace-global overview partition) takes the full load. The rule earned its wording five grades running, each catching the next surface over: `memstead_entity include_relations` silently dropped 11 of 25 incoming edges; mem-scoped `memstead_health` reported 28 false dangling links (its adjudication walks the whole graph); the DESTRUCTIVE guards — entity delete's `HAS_INCOMING_REFS` and mem delete's `MEM_HAS_INCOMING_REFS` — silently deleted what an eager boot refuses, because incoming referrers in unloaded mems were invisible; the write-time ACYCLICITY guard admitted a cycle whose mid-path edge lived on a deferred mem's entity (relate loads only its endpoint mems; the next eager boot then dropped an innocent pre-existing edge to break the on-disk cycle); and the fix reached only the SINGLE mutation paths — the batch paths (`batch_relate`/`batch_create`/`batch_update`, the shape MCP routes multi-relation calls to) bypassed it and committed the same cycle live, and the CLI's `full_engine` seam (mem list, recover, the batch commands, install/uninstall) never loaded at all, rendering unloaded mems as entity count 0. All fixed by full-loading before the cross-mem answer — single AND batch mutation paths ensure the full load whenever an involved rel-type is acyclic, the CLI's `full_engine` seam full-loads like its siblings, and the mem-rename reference sweep and parse recovery (both workspace-answer-scope) load fully before acting. The closing act was the inventory the grades kept proving missing: a one-time sweep of every entry point reaching `prepare_*` or the store against its load scope — wrappers delegate to guarded paths, `record_check`/`changes_since` are genuinely mem-local, and the one `&self` adjudicator (`classify_delete_referrers`) cannot load and so carries a fully-loaded-engine precondition its callers all satisfy. The destructive and integrity guards are the sharpest cases: their failures destroy or corrupt data rather than misreporting it. Loading rides the ordinary per-mem reload — the same entity walk, store push, workspace-global validation passes, and memo invalidation — so deferral changes WHEN the gauntlet runs, never whether; a failed deferred load quarantines at first read with the eager path's typed reporting. Cross-mem links into a deferred mem are stubs until it loads, resolve on arrival, and pending nested-prefix warnings re-filter against the completed store. Opt-in per mount; nothing flips defaults. On the CLI the safe default loads everything after boot; commands whose whole answer lives in one mem opt into a scoped accessor (`memstead entity` first — its `--include-relations` form, whose incoming edges can originate anywhere, keeps the full load).

## Context
Every boot loaded every mount in full at a measured 0.36–0.75 ms/entity — the sizing curve named lazy mounts "the largest lever the curve can see", and the VISION's federated many-small-mems tier was priced out by it. The `Lazy` slot had existed since V1, persisted and documented (GLOSSARY: "loaded on first access") but behaviourally inert — the docs promised what the code did not do. The structural crux was the three workspace-global boot passes that assume a complete store; the resolution reuses the reload path, which already re-runs them per-mem-arrival. Measured on the dogfood workspace (9 mounts, 687 entities, release build, median of 10 cold runs): scoped `memstead entity` with 8 of 9 mounts lazy dropped 237 ms → 106 ms, output byte-identical to eager; the workspace-scoped path stayed ~300 ms by design; overview under lazy renders all nine mems with true counts.

## Consequences
The federation pattern stops paying the whole inventory per touch: cold cost is proportional to the mems actually read, on the engine, MCP, and the scoped CLI path — with the caveat the grades taught: the funnel's existence is not the guarantee; each handler's LOAD SCOPE must match its ANSWER SCOPE, and five consecutive grades each found one more surface where they diverged (read forms, health, delete guards, the acyclicity guard, then the batch paths and the CLI's non-loading seam). The durable lesson is methodological: per-surface patching converges only after an explicit inventory of every entry point against its load scope — the inventory, not the funnel, is what makes "no answer over a partial store" a checkable claim. A lazy mem is never silently absent — the roster carries it with its pin, `deferred_mems()` / `mem_is_deferred()` expose load state, and every counting surface either triggers the load or must render the state (bare zeros are the forbidden rendering; `mem list` is pinned on this). One latent trap became live and is pinned: the test-helper archive mount had carried the aspirational `Lazy` value since V1 and broke eight archive tests the moment the slot became real — any embedder constructing mounts directly and reading `engine.store()` without an operation funnel inherits the same hazard, as does any embedder calling the `&self` referrer classifier on an unloaded engine. Realized in the engine's boot/lifecycle/drift seams and measured in `docs/sizing-curve.md`.

## Options

Rejected: lazy-by-default for read-only/archive mounts (a behaviour flip for existing workspaces hitchhiking on the mechanism; defaults are a separate decision). Rejected: deferring the global passes until all mems load (a mostly-lazy workspace would serve indefinitely with cross-mem validation never run; the passes' guarantees hold for the loaded subgraph and discharge per arrival instead). Rejected: skipping the metadata half at boot (the roster must know the mem exists with its pin — observability is the SPEC's binding constraint). Chosen for the CLI: full-load-by-default with per-command scoped opt-in, so an unaudited command can never read a partial store — correctness is the default posture, speed is opted into where the answer provably lives in one mem.
